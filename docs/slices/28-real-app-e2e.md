# Slice 28 – End-to-end tests of the real app

Planned on 2026-11-15 and approved by the user the same day; implementation starts with step 1 of the Plan.

## Context

The Playwright tests in `ui/e2e/` run the UI in a plain browser against a fake `window.__TAURI_INTERNALS__` (`ui/e2e/tauri-mock.ts`). They test the UI flows well, but no Rust code runs: there are no real windows, no plugins, no main thread and no event loop. Two bugs in slice 7 lived in exactly that gap:

- **v0.6.2** froze when opening the viewer. `open_viewer` placed the new window from its command thread while holding the window-state plugin's lock, and the plugin's window registration on the main thread waited for that lock. The mock just returns `null` for `open_viewer`, so the e2e tests never saw it.
- **v0.6.3** forgot window sizes across restarts, because closing the last window on Windows did not reach the plugin's save on exit. No test closes and restarts the real app.

As a stopgap, the release smoke test now opens the viewer in the installed app and closes it again (`SITO_SMOKE_TEST=1`, `src-tauri/src/smoke.rs`). It fails on a freeze, a viewer that does not appear, or a missing window state file. On Linux under Xvfb it reproduces the v0.6.2 freeze. But it only runs on releases and tests a single flow.

## Concept

Drive the built app, not a mock, with WebDriver through [`tauri-driver`](https://v2.tauri.app/develop/tests/webdriver/), on every push and pull request. The mocked Playwright suite stays as it is: it remains the fast, broad test of the UI flows; the new suite is a handful of slow tests of what only the real app can show (windows, plugins, threads, the file system, restarts).

## Decisions

These settle the open questions of the draft.

- **Runner: WebdriverIO with Mocha and [`@wdio/tauri-service`](https://webdriver.io/docs/desktop-testing/tauri)**, the setup the Tauri docs recommend. The service starts the driver for each session and keeps the Edge WebDriver in sync with WebView2. Playwright `connectOverCDP` to WebView2 was considered and dropped: it works on Windows only and drives one webview per connection, while the tests need both windows and should also run on Linux and macOS.
- **Platforms and drivers:** one suite, one driver per platform, chosen by the service's `driverProvider`:
  - `windows-latest`: `tauri-driver` with Edge WebDriver for WebView2 (provider `official`). This is the platform users have, and the driver sends real browser input.
  - `ubuntu-latest` under Xvfb: `tauri-driver` with `WebKitWebDriver` (provider `official`). It is cheaper, and it reproduced the v0.6.2 freeze.
  - `macos-latest`: Apple has no WebDriver for WKWebView, so the app itself serves one: [`tauri-plugin-wdio-webdriver`](https://docs.rs/crate/tauri-plugin-wdio-webdriver/1.3.0/source/README.md) (MIT, provider `embedded`) runs a W3C WebDriver server inside the app on `127.0.0.1:4445`, with window handles, switching and window rects. It is young (a 2026 fork of `tauri-plugin-webdriver`), and its input is likely synthetic DOM events rather than OS input; for this suite that is enough, since the bugs it looks for are in windows, threads and files, not in input handling. CrabNebula's fork of `tauri-driver` also covers macOS but needs a paid key, so it is not used.
  - Why not the embedded driver everywhere: on Windows and Linux the official drivers are mature and send real input; the embedded one is kept to where nothing else exists.
- **The embedded driver is never shipped.** It exposes automation over HTTP (its README: never in production builds), so it sits behind a cargo feature `e2e` of `src-tauri` (off by default, not `cfg(debug_assertions)`, so `npm run tauri dev` never opens that port either), and its permission (`wdio-webdriver:default`) is granted only by the e2e config's inline capability (see below). Only the e2e build turns the feature on (`tauri build --debug --no-bundle --features e2e`). It is registered on every platform the feature is on but only used on macOS; the Windows and Linux jobs build without the feature.
- Locally the suite runs on the Mac (embedded driver) and on the Windows dev machine (official driver).
- **The app under test** is a debug build with the bundled frontend: `tauri build --debug --no-bundle --config src-tauri/tauri.e2e.conf.json`. Debug, so it builds fast and reads the debug-only `SITO_UPDATE_ENDPOINT`; bundled frontend (`custom-protocol`), so no Vite server runs and the pages load from `tauri://` as in the installed app.
- **Its own identifier.** `tauri.e2e.conf.json` overrides `identifier` with `io.github.lukaszkalnik.sito.e2e`. All the app's state lives under that identifier: the action log and the photo cache (app data and cache folders), the window state (config folder) and the webview storage with the last folder (WebView2's `EBWebView` in the local app data folder; WebKitGTK's data folder on Linux). So a test run on the dev machine never touches the real Sito's data, and the installed Sito never sees the tests'. On Windows the folders cannot be moved by environment variables (Tauri finds them through the Known Folders API, not `APPDATA`), so this is the only isolation that works there.
- **Fresh state per test.** Before each spec, the harness moves any folder of the e2e identifier left from an earlier run into that run's results folder; after the spec, it moves the spec's state folders into the spec's results folder. Nothing is deleted, and a failed test leaves its action log, window state and debug log behind as a CI artifact. On Linux the harness also points `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` at the spec's temp folder, so the trash (in `XDG_DATA_HOME`) is the test's too.
- **Photos:** each spec builds its gallery in a new temp folder from copies of `fixtures/` (keeping modification times, as `crates/core/tests/moved_photos.rs` does), under a name with Polish letters (`Zdjęcia – próba`) so the real paths cover non-ASCII. Tests never read a real photo folder.
- **Opening a folder without the dialog:** the native folder picker cannot be driven over WebDriver. Instead of a test-only start parameter or command, the harness uses the app's own reopening of the last folder (slice 9, [Reopening a folder](../domain/timeline.md#reopening-a-folder)): it writes the gallery path to `localStorage` under `sito.lastFolder` with WebDriver's `execute` and reloads the main window. The app then opens the folder through `start_scan` exactly as on a normal start. No app code exists only for tests. Fallback if the reload turns out to be refused or unreliable: a debug-only `SITO_E2E_FOLDER` read by a `startup_folder` command, which then gets its own unit test.
- **No network:** tauri-driver starts the app with `SITO_UPDATE_ENDPOINT=http://127.0.0.1:9/latest.json` (a closed port), so the update check on start fails at once and quietly (the notice shows nothing on an unreachable server, see [Updates](../domain/updates.md#the-notice)), and the tests never reach GitHub.
- **Moving and resizing windows:** done through Tauri's own window API from the page (`setSize`, `setPosition`, `outerSize`, `outerPosition`), which acts on the native window the window-state plugin saves, rather than WebDriver's `setWindowRect`, which WebView2's driver may apply to the webview only. The shipped capabilities do not allow these calls and stay unchanged: `tauri.e2e.conf.json` lists the capabilities explicitly (`app.security.capabilities`: `default` plus an inline `e2e` capability with `core:window:allow-set-size`, `allow-set-position`, `allow-outer-size`, `allow-outer-position` for `main` and `viewer`). Only the e2e build has them; stated reason: tests must place windows to check that they come back.
- **Closing like a user:** the viewer through its „Zamknij” button, the main window through `getCurrentWindow().close()` (allowed by the shipped `core:window:allow-close`). Like a click on the close button, it emits `CloseRequested`, so `window_fit::save_on_close` runs, as in the smoke test.
- **Edge WebDriver:** must match the runner's WebView2 runtime (the runner's preinstalled `msedgedriver` matches Edge, which need not be the WebView2 version). `@wdio/tauri-service` fetches the matching one; if that proves unreliable on CI, `msedgedriver-tool` (pinned, `cargo install --locked`) as in the older Tauri docs.
- **When CI runs it:** on every push to `main` and every pull request, except when only `docs/**` or Markdown files change (`paths-ignore`). With `Swatinem/rust-cache` a warm debug build should take a few minutes; if the Windows job turns out much slower than the existing CI, revisit (e.g. only when `src-tauri/`, `crates/`, `ui/` or the suite change).
- **The smoke test on pull requests** (the draft's cheap first step) comes first, in the Linux job: before the WebDriver specs it runs the e2e build once with `SITO_SMOKE_TEST=1` under `xvfb-run` and a 60 s timeout. It takes seconds and fails with a clear exit code on a window freeze even if the WebDriver setup itself breaks.

## Plan

One commit per step, each with CI green.

1. **Linux smoke test on every push (`ci:`).** New workflow `.github/workflows/e2e-app.yml` (permissions `contents: read`, pinned actions, `persist-credentials: false`, `paths-ignore` as above). Job `linux`: apt-get the Tauri Linux build dependencies (`libwebkit2gtk-4.1-dev`, `librsvg2-dev`, `libxdo-dev`, `libssl-dev`, `build-essential`, `xvfb`, `webkit2gtk-driver`), Rust stable, `rust-cache`, Node 24, `npm ci`, build the e2e app (step 2's config; until then plain `--debug --no-bundle`), then `SITO_SMOKE_TEST=1 timeout 60 xvfb-run -a target/debug/sito` with the exit codes mapped to messages as in `release.yml`. Upload the app's debug log on failure. `zizmor .github` clean.
2. **The e2e build config (`ci:`).** `src-tauri/tauri.e2e.conf.json` (identifier, explicit capabilities with the inline `e2e` capability) and a root script `npm run e2e:app:build` (`tauri build --debug --no-bundle --config src-tauri/tauri.e2e.conf.json`). Check that `tauri build` without the e2e config still produces the shipped capabilities only (the generated `gen/schemas/capabilities.json` lists no `e2e`) and that no Rust code depends on the identifier.
3. **The embedded driver for macOS (`test:`).** Optional dependency `tauri-plugin-wdio-webdriver` (pinned) and feature `e2e = ["dep:tauri-plugin-wdio-webdriver"]` in `src-tauri/Cargo.toml`; in `lib.rs` a `#[cfg(feature = "e2e")]` registration in its own small function (a module `e2e.rs` if it grows). A second config `src-tauri/tauri.e2e-embedded.conf.json` (or one more inline capability, if the CLI merges it cleanly) grants `wdio-webdriver:default`; a capability naming a plugin that is not compiled in would fail the build, so the shipped and the Windows/Linux e2e configs do not mention it. Root script `npm run e2e:app:build:mac` adds `--features e2e`. License: MIT is on the reviewed list; check the plugin's own dependencies with `cargo about` and run `cargo audit`. Since the dependency is optional and off in shipped builds, check whether `cargo about` (run over the workspace) lists it in `ui/notices/rust-crates.txt`; if it does, that is harmless (a notice for an unshipped crate) but say so in the commit. A unit test is not needed (no logic), but `cargo clippy --all-targets --features e2e` joins the lint step of the macOS job so the feature code stays clean.
4. **The suite and its harness (`test:`).** New npm workspace `e2e-app/` (root `package.json` `workspaces`), strict TypeScript, devDependencies `@wdio/cli`, `@wdio/local-runner`, `@wdio/mocha-framework`, `@wdio/spec-reporter`, `@wdio/tauri-service`, `webdriverio`. Layout by concern, one concept per file:
   - `wdio.conf.ts`: capabilities `{ 'tauri:options': { application: <target/debug/sito[.exe]> } }`, host `127.0.0.1:4444`, one worker (`maxInstances: 1`, the dev machine has 7 GB), Mocha timeout 60 s, spec reporter, results folder `e2e-app/results/`. `beforeSession` spawns `tauri-driver` with the app's environment (`SITO_UPDATE_ENDPOINT`, on Linux the `XDG_*` folders; `--native-driver` pointing at the matched `msedgedriver` on Windows) and `afterSession` stops it.
   - `support/appState.ts`: the e2e identifier's state folders per platform, and moving them aside before and after a spec.
   - `support/gallery.ts`: builds a temp gallery from `fixtures/`, with the expected photo and series counts next to it (derived from the tables in `fixtures/README.md` and the grouping rules, written down as constants with a comment saying where they come from).
   - `support/app.ts`: `openFolder(path)` (seed `sito.lastFolder`, reload, wait for the grid), `switchToWindow('main' | 'viewer')` (by window handle, matched by URL: the viewer is `index.html?window=viewer`), `waitForViewer()`, `windowRect()` / `placeWindow()` / `closeWindow()` over Tauri's window API, `restartApp()` (`browser.reloadSession()`, which quits and starts the app with the same state folders).
   - Selectors by role, label and text (WebdriverIO `aria/` and text selectors), never CSS classes, as in the mocked suite. Polish strings come from `ui/src/i18n/pl.json` where a test needs them, so a wording change does not break the suite silently.
   - Lint and types: `e2e-app` gets `lint` (oxlint with the ui's rules, Prettier) and `typecheck` scripts, run by the root `npm run lint` / a root typecheck, and by the frontend CI job.
   - Root script `npm run e2e:app` (build, then `wdio run e2e-app/wdio.conf.ts`).
5. **The first specs (`test:`),** run locally on the Mac first (embedded driver), then on CI, one file per scenario (see [Tests](#tests)): `scan.spec.ts`, `viewer.spec.ts`, `reject.spec.ts`, `restart.spec.ts`. Each starts from fresh state and its own gallery.
6. **Run them on CI (`ci:`).** In `e2e-app.yml`: the Linux job runs `xvfb-run -a npm run e2e:app` after the smoke test; a `windows` job does the same on `windows-latest` (no Xvfb); a `macos` job on `macos-latest` builds with `--features e2e` and runs the suite with the embedded driver (the macOS runner has a logged-in GUI session, so windows open and can be placed). `tauri-driver` installed with `cargo install --locked --version <pinned>` (cached by `rust-cache`, which keeps `~/.cargo/bin`). The macOS job also runs the smoke test first, as the Linux one does, so the release smoke test's macOS gap closes on every push. On failure, upload `e2e-app/results/` (screenshots taken by an `afterTest` hook, the specs' state folders with the debug log).
7. **Docs (`docs:`).** `CLAUDE.md`: the two e2e suites (mocked Playwright for UI flows, real-app WebdriverIO for windows, restarts and files; which one a new test belongs in), `npm run e2e:app` in Commands, `e2e-app/` in the layout, the new workflow in the CI section. `docs/RELEASING.md`: the smoke test now also runs on every push (Linux and macOS). Doc comment of `src-tauri/src/smoke.rs`: it no longer says the e2e tests cannot see freezes; it is the release check of the installed app and the macOS stand-in. `docs/domain/security.md`, release pipeline: the e2e build, its extra window permissions and the embedded WebDriver (feature `e2e`) are never shipped. The roadmap and this file get the status.

Not in this slice: the installer and update path ([slice 42](42-zero-click-update.md)), rejecting into the trash on CI (the Windows runner's recycle bin is real but untested here; can follow once the suite is stable), and moving existing mocked tests over.

## Tests

The specs of step 5. "Within a few seconds" means a WebdriverIO `waitUntil` with a timeout (10 s on CI), never a `sleep`.

1. **Scan** (`scan.spec.ts`): open the gallery → the photo count in the bar and the number of series in the grid match the gallery's expected values; the thumbnails load (an `img` in a tile reports `naturalWidth > 0`, i.e. the `thumb:` protocol answered).
2. **Viewer opens and is reused** (`viewer.spec.ts`): click a photo of a series → a second window handle appears within a few seconds (the v0.6.2 freeze fails here) and the viewer shows that photo's name; back in the main window click another photo → still two window handles, and the viewer shows the new photo.
3. **Stepping** (same spec): in the viewer, → and ← step through the series in the grid's order (the names change as expected, the strip marks the current photo); at the end of the series → goes on to the next photo of the view.
4. **Reject and undo** (`reject.spec.ts`): reject the photo shown in the viewer („Odrzuć”) → the file is gone from its folder and is in `Odrzucone` next to it, on disk (checked by the test with `fs`), the main window's count drops by one; „Cofnij” → the file is back under its own name and `Odrzucone` holds nothing of it; the count is back.
5. **Restart** (`restart.spec.ts`, the v0.6.3 case): open the gallery and the viewer, place both windows at known sizes and positions (different from the defaults and from each other, inside the screen), close the viewer with „Zamknij” and the main window like a user → the app exits and the e2e identifier's `.window-state.json` holds both windows; start the app again → the gallery reopens by itself (from the photo cache) with the same count, and opening the viewer brings it back at its size and position; the main window is at its own. Sizes and positions are compared with a small tolerance for frames. Under Xvfb without a window manager positions may not be kept: if so, the Linux run checks sizes only, with a comment saying why. On macOS, window positions are in points and the menu bar shifts the top edge; the tolerance and the work area come from the same Tauri calls, not from fixed numbers.

No unit tests in `core` or `ui`: the slice adds no app logic. The harness helpers are test code; `gallery.ts`'s expected values are checked by spec 1 itself. If the fallback for opening a folder is needed, its parsing of `SITO_E2E_FOLDER` gets a unit test like `smoke::enabled`.
